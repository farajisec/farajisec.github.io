About

I run the infrastructure of a university computer science department — the GPU clusters, research servers, storage, identity and monitoring that faculty and students depend on — and I spend the rest of my time on the detection side of the same problem: how an attacker would move through an environment like mine, and how to see it.

Three years as the department's senior systems administrator, finishing an M.S. in Cybersecurity, and building a portfolio of detection-engineering work that is measured rather than claimed: every project below ships with labeled data, an evaluation harness and a CI run that fails if the numbers regress.

Projects

siem-detection-lab

A from-scratch Sigma rule engine with correlation rules, behavioural analytics (beaconing, impossible travel, DGA, exfiltration volume), risk-based incident grouping and an evaluation harness, run against a synthetic week of identity and network telemetry with 22 labeled attacks, 9 benign look-alikes and a six-stage account-takeover campaign.

15 detections · recall 1.0 on the scenario set · 0 alerts on plain baseline · campaign rebuilt into one incident · exports to Sentinel KQL and Splunk SPL

log-anomaly-triage

Unsupervised, multi-signal anomaly detection for service metrics — minute-level seasonal profiles, EWMA, bias-corrected CUSUM and a load-decoupling model fused into an advisory, explained triage queue with change-aware hold-outs and an analyst feedback loop that recalibrates detectors within bounds.

10 / 10 incidents detected · precision 0.55 vs 0.06 for a naive z-score · ~1 candidate per day across six services · the package cannot act, and a test proves it

csflow

A privacy-first fleet status pipeline: counts-only aggregation, a publish delay, and a fail-closed privacy gate that scans every published artifact so a public status page cannot leak a single hostname.

Built for the problem of showing a department its fleet is healthy without handing an outsider a map of it
